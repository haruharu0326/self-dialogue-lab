# 応答評価CLI

2026-10-25 仕様初稿。通常画面と本人用DBから独立した開発用機能です。

## 要件

- EFR-001：版付きの架空ケースを本番のGeminiResponderに渡し、反復実行する。API呼出しは明示的な `--live` 指定時だけ行う。既定はモック・固定応答による基盤の動作確認。
- EFR-002：入力、履歴、返答、実行時刻、モデル、プロンプトと生成設定のハッシュ、ケースのハッシュ、実装ハッシュ、所要時間、成功・失敗をローカルJSONへ記録する。本人用DBを開かない。出力を上書きしない。
- EFR-003：形式・参照の自動チェックと、人による忠実さ・決めつけ回避・問いの有用性の0〜2点採点を分離する。未採点を0点と扱わない。同一ケース・同一実行種別の結果だけ比較し、条件差と標本数を表示する。
- ENFR-001：出力はGit対象外の `.eval-runs/` を標準とし、生の例外やキーを保存しない。モック成功をGeminiの対話品質と呼ばない。実APIの実行は有料になり得るため通常テストでは実行しない。

## 設計と手順

`python scripts/evaluate.py run --output .eval-runs/baseline.json`

既定は同梱の架空ケースをモックで実行します。`--live` を付けると、環境変数のGemini設定でGoogleへ架空入力を送信します。`.env` の自動読込はありません。`--repeat 3` で反復できます。`--cases PATH` は同じ形式の架空ケース専用JSONです。実情報を入れないでください。

ケースは `version`、`fictional: true`、一意な `id` を持つ `cases` 配列からなります。各ケースの `turns` は複数の本人発言を持てます。生成した応答を次のターンの短期履歴へ渡します。記憶はケースで指定した現在の記憶だけで、応答から自動保存しません。

出力の各 `results` の `scores` を人が編集します。`faithfulness`（発言に忠実）、`non_assumption`（決めつけ回避）、`useful_question`（理由・前提・別の見方を考える助け）を、0=問題あり、1=一部満たす、2=満たすで採点し、`note` に理由を書きます。複数ターンは一連の対話として採点します。人の評価を自動的な合否にはしません。

`python scripts/evaluate.py compare .eval-runs/baseline.json .eval-runs/candidate.json`

実行器 → GeminiResponder（または明示された固定モック）→ JSON成果物 → 人の採点 → 比較、の構成です。画面・Storeへの依存はありません。トークン使用量・料金、モデルによる自動採点、過去版プロンプトの自動切替は今回の対象外です。モデルの別名が更新される場合もあるため、条件ハッシュだけで完全再現を保証しません。

## 受入条件

EAT-001：モックで多ターン・反復・保存・CLI起動が成功し、実APIを呼ばない。

EAT-002：不正ケースは呼出し前に拒否。失敗を安全に記録し、既存成果物を上書きしない。

EAT-003：未採点・失敗・条件差を含む比較を検証し、異なるケースやモックと実APIの比較を拒否。

実施結果は[受入テスト仕様書](../testing/acceptance-tests.md)を参照。
